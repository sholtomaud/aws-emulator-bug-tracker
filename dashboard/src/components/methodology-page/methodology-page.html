Methodology

How the numbers are calculated

Why the AWS emulator?

AWS says the emulator was built entirely by autonomous AI agents. The argument here is simple: if agents can do 100% of the development, they should also be able to resolve 100% of the issues, bugs and feature requests.

AWS is also one of the largest software development organisations on Earth, so its agentic workflows, including how issues are tracked and closed, should demonstrate best-in-class practice. The dashboard measures how close they are.

Every number on the dashboard comes from files that a GitHub Actions workflow rebuilds on a schedule, chiefly data.csv, from the public issue tracker and repository of .

The data

Each row is a UTC day, and each column is a running total as of the end of that day:

open
Issues open on that day.
agent_closed
Issues closed so far by an AI agent: a GitHub Bot account, or a login containing agent, bot, emulator-ai or automation.
human_closed
Issues closed so far by anyone else.

Pull requests are not counted. The newest row is the day in progress: it is rewritten on every run, and rates count it as the part of a day that has passed, not a whole one.

The Doomsday Clock

Hours to midnight = (1 − agent resolution share) × 24

The agent resolution share is the fraction of all closed issues that an AI agent closed. The clock runs over one day on a 24-hour dial. At 0% it reads 00:00, the start of the day, with a full 24 hours to go; every 1% of agent share moves it on about 14 minutes. At 100% it reaches 24:00, the midnight that ends the day, and human engineers have been replaced on this tracker.

  • Safe: more than 18 hours to midnight (before 06:00; agent share under 25%).
  • Elevated: 12 to 18 hours (06:00 to noon).
  • Severe: 4 to 12 hours (noon to 20:00).
  • Critical: 4 hours or less (after 20:00).

Agent velocity

The speedometer shows how many tickets AI agents close per day, averaged over the last seven days (or all the data, while there is less than a week of it). Two marks on the dial give it context:

  • Humans: tickets closed per day by people over the same window.
  • New issues: the arrival rate, the change in open plus closed issues per day.

The red redline starts at the arrival rate. Once the needle passes it, agents are closing tickets faster than they are filed and the backlog shrinks without human help.

Bug doom loop

Doom loop ratio = issues opened ÷ issues closed (last 7 days)

The dashboard shows it twice, in the same form, once for each queue: the public GitHub issues, and the agents' own queue, where it is problems filed ÷ problems resolved. Side by side they show whether each list is shrinking or growing.

Issues opened are the change in open plus closed issues; issues closed count both agents and humans. Above 1× the backlog grows however hard everyone works. The meter uses a log scale from ⅛× to 8×, so halving and doubling look the same distance from break-even.

  • Burning down: under 0.9×, the backlog is shrinking.
  • Holding steady: 0.9× to 1.1×.
  • Falling behind: 1.1× to 2×.
  • Bug doom loop: over 2×, or issues arriving with none closed.

The projection divides today's open backlog by the net daily change: how long until it doubles, or until it is empty.

The two queues

The emulator has two lists of problems, and the dashboard tracks both.

  • Public GitHub issues: what people using the emulator report. The clock, the speedometer and the doom loop are all measured on this list, because it is the one users can see and rely on.
  • The agents' own queue: files inside the repository. One agent files each problem it finds under issues/things-that-do-not-work/; another commits a fix and moves the file to issues/things-that-now-work/.

For the agents' queue the tracker counts the files in those two folders at the last commit of each day; it reads nothing else from the repository. Resolved per day is the growth of the second folder. New per day is the growth of both together, so a problem the agents retract counts as one fewer filed.

How issues were closed

An issue marked closed is not necessarily an issue fixed. For every closed public issue the tracker reads the closing event and the last 20 comments, and puts it in one of five groups:

Fix referenced
A commit or merged pull request closed it, or someone other than the reporter pointed to a commit, a release, or the agents' "now works" record in a comment.
Closed without a referenced fix
Marked completed, with nothing recorded to check it against.
Declined
Closed as "not planned".
Withdrawn
Closed by the person who reported it, with no fix referenced.
Duplicate
Closed as a duplicate of another issue.

The doom loop panel also shows the ratio counting only closures that reference a fix. The distance between that figure and the headline ratio is how much of the closing activity cannot be verified from the record.

Two limits. A genuine fix that nobody linked lands in "closed without a referenced fix", so that group is an upper bound on unverified closures, not a finding about any one of them. And the tracker checks that a fix is referenced, not that the fix is correct.

Why a referenced fix is the test

The emulator does not accept pull requests; agents commit straight to the main branch. That leaves the reference from a closed issue to a commit or release as the only public trail connecting a report to its fix. Without it, a reader has to take the closure on trust. This is what we would expect a best-in-class workflow to record:

  • Every fix links to its issue. A commit message that says "Fixes #123" makes GitHub close the issue and record the commit with no extra work, which an agent can do every time.
  • The closing comment says where the fix shipped: the commit or release, so the reporter can confirm it.
  • The closing reason is accurate: completed, not planned, or duplicate with a link to the original.
  • Every issue is typed at triage with a label or issue type, so the backlog can be measured by kind.
  • Internal and public queues are linked. When work tracked elsewhere resolves a public issue, each record points to the other.

The agents already do most of this in their own queue: each fix commit names the problem file it resolves. The same practice applied to public issues would make every closure verifiable.

Issue types

The emulator offers two issue forms, and the form's headings stay in the issue text. The tracker reads the type from them, and from labels where they exist:

  • Behaviour differs from AWS: the bug-style report ("What happened"), or a bug label.
  • Feature request: the feature form ("Use case"), or a feature-request label.
  • Other: anything that used neither form.

The doom loop panel shows the ratio for behaviour reports only alongside the headline, since a backlog of unfixed bugs and a backlog of unbuilt features are different problems.

Agent time to clear backlog

Today's open issues divided by the agents' daily rate: how long agents alone would take to empty the tracker if no new issues arrived. It reads Never while agents close nothing.
